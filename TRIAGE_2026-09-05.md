## The three that need more than a line

### 22b — the zeroed run is not a bug, it is the ruling

This is the item to settle first, because it is the only one where a fix moves the money.

The reducer is doing exactly what it was told. `stage === "mark"` in `sandboxSession.ts` carries the
ruling verbatim:

> "loses its lowest value train. **It receives no standard route revenue for this submission.** Instead,
> award the corporation cash equal to 0.5x the deleted train's depot value."

So it zeroes `last_route_revenue` *and* `printed_route_revenue` — the second deliberately, because
`printed_route_revenue` is what the next roll accumulates onto (#941), and leaving it would pay for these
routes again on the corporation's next dispatch. That is #934's double-payment, guarded on purpose.

Your feedback says the *other* train's legal run should still pay, and the 0.5x covers only the train that
was taken. That is a **different rule** from the one on record. Both are coherent; they are not the same
ruling. Which means:

- This is a **spec change**, so no amount of code reading will settle it — you have to.
- The fix lands in the reducer, so **the server inherits it**. Settle it before the migration or you port
  a rule you are about to change.
- It **changes how existing logs replay** — same category as #1184, and it wants the same knowing approval.

The narration half is separate and is an ordinary bug: `fleetLossNotices` derives its `"limit"` cause from
`describeFleetLosses(before, after)`, which diffs fleets. The Mark *removes* a train, the diff sees a
fleet shrink, and a limit notice is a plausible thing for it to emit — but a corporation that just **lost**
a train cannot be over the limit. That one is safe to fix now and does not wait on the ruling.

### 6 — the flashing is real, and the server will not fix it

Confirmed in the log. Auto-skip does not jump; it **emits one logged action per skipped subphase**:

```
44  derived  AdvanceOperatingSubPhase  protocol_id 7
45  derived  AdvanceOperatingSubPhase  protocol_id 7   +271ms
46  derived  DeclareDividends          protocol_id 7   +271ms
```

Same shape at 52/53, 65–67, 90–92, 226/227. The Action Bar is rendering each intermediate state
faithfully, ~270ms apart, which is precisely long enough to see.

**This is a granularity decision, not a rendering bug**, and it is worth making before the migration: an
authoritative server replaying these will emit the same intermediate states and the same flicker. The
options are to collapse a skip run into one action, or to have the client suppress intermediate frames.
The first is a log-format change and belongs with the audit; the second is local. Worth choosing now
because the answer changes the wire format.

### 24 — measure this before calling it corruption

There is a mechanism that produces exactly this symptom without any desync, and this log has it.

`last_route_revenue` is the **variant-adjusted** figure — `#903` applies the die there, and `gameState.ts`
is explicit that "Last Run" is a claim about money, not about printed route value. This room ran with
`unpredictableRevenue: true`. So the card is *supposed* to differ from what the routes print.

On top of that, the roll is applied to `printedTotal`, which **accumulates** within a turn (#968, kept
deliberately so a corporation running twice does not lose the money). Indices 318/319 are the proof:

- 318 → printed 270 → roll applied to **270**
- 319 → printed 540 → roll applied to **540**

So a turn with a duplicate run rolls the die on a doubled base, and the card reports the adjusted figure of
a number nobody plotted. That is not corruption; it is three correct behaviours compounding.

**The test:** replay `sandbox-log-JUNO-3XD.json` headless and compare each corporation's
`last_completed_run_revenue` against the `revenue_amount` its own `DeclareDividends` carried. If they
line up, item 24 is a labelling and expectation problem and the fix is on the card, not in the reducer.
If they do not, there is a real bug and now there is a fixture that reproduces it.

This is also the first concrete argument for the extraction: that test needs the reducer runnable outside
React, which is the same work as putting it on a server.
